# Komintern WebSocket Server

Node.js + TypeScript Socket.io server that orchestrates the Python game engine for the social deduction game.

## What This Server Does

- Manages in-memory rooms (no database).
- Starts one Python engine process per active game session.
- Enforces server-side game flow rules:
  - phase validation,
  - chef turn validation,
  - confidence vote collection,
  - mission vote collection.
- Preserves information asymmetry by sending per-player views only.
- Preserves mission vote anonymity by forwarding shuffled mission votes from Python without attribution.
- Supports the updated ruleset-driven engine while keeping the original 5-player flow as the default.

## Project Structure

- src/index.ts: process entry (env, listen, signals, crash handlers).
- src/app.ts: `createKominternApp()` — Socket.IO server and all socket handlers (testable).
- src/validation.ts: one validator per client payload field.
- src/events.ts: all client/server event constants.
- src/types.ts: payload types (room, resync, histories).
- src/PythonBridge.ts: NDJSON bridge with request ids, timeouts and crash detection.
- src/RoomManager.ts: rooms, seats, reconnection, AFK, cleanup, replay.
- src/GameSession.ts: serialized game state machine for one room.
- src/rulesets.ts: presets and ruleset validation (mirror of the engine).
- src/logger.ts: JSON line logger (`LOG_LEVEL`).
- src/*.test.ts: unit tests; src/e2e.test.ts plays full games against the real engine.

## Socket Event Contract

All names live in src/events.ts. Every payload is validated; invalid actions get
`error { code, message }`.

### Identity and reconnection

Player ids are generated by the server and are public. Reclaiming a seat (reload, network
drop) only works with the client's secret `playerUid` (16-128 chars), which is never sent to
other clients. New players can only join while the room is in the lobby.

### Client -> Server

- create_room { code?, pseudo?, playerUid?, ruleset_preset?, ruleset? }
- join_room { code, pseudo?, playerUid? }
- set_pseudo { pseudo }, leave_room {}
- start_game { ruleset_preset?, ruleset? } (host only)
- table_order_tap {}, table_order_adjust { position }, table_order_confirmed {}, table_order_back {} (host)
- role_confirmed {}
- propose_team { team } (current chef)
- confidence_vote { vote: "yes" | "no" }, confidence_result_confirmed {}
- mission_vote { vote: "nazi" | "communist" }, mission_result_confirmed {}
- end_game_confirmed {}, replay_choice { choice: "replay" | "quit" }

### Server -> Client

- room_joined { playerId, ...room } (to the joining socket only)
- room_updated { players, code, hostPlayerId, targetPlayerCount, status }
- player_left { playerId }, player_afk { playerId }
- game_started, game_aborted { reason }
- table_order_updated, role_assigned { role, roleMap?, turnOrder }
- proposal_phase { chef, missionSize, missionIndex, team }, confidence_phase { chef, team }
- confidence_revealed { votes, result, approved }
- mission_phase / mission_progress { team, votesSubmitted, votesRequired, submittedPlayerIds }
- mission_revealed { missionIndex, team, naziVotes, result, scores }
- game_over { winner, reason: "missions" | "forfeit", forfeitedBy?, scores }
- roles_revealed { roleMap }
- resync (full state for a reconnecting player, including histories and "already voted" flags)
- error { code, message }

## Python Bridge Protocol

Transport: newline-delimited JSON over stdin/stdout. Every request carries an `id` that the
engine echoes, so stray output lines are ignored instead of shifting responses. Each command
has a timeout (ENGINE_TIMEOUT_MS); a hung or crashed engine aborts the game and the room goes
back to the lobby.

```json
{"id":1,"command":"start_game","args":{"player_ids":["p1","p2","p3","p4","p5"],"chef_cursor":0,"ruleset_preset":"PRESET_5J"}}
{"id":1,"ok":true,"result":{"status":"ok","round":{"mission_index":0,"chef_id":"p1","required_team_size":2,"scores":{"nazi":0,"communist":0}}}}
```

Commands: start_game { player_ids, chef_cursor, ruleset_preset? | ruleset?, seed? },
get_player_view { player_id }, get_game_state, get_round_state, set_turn_order,
propose_team { team, proposer_id? }, submit_confidence_votes { votes, voter_ids? } (returns
`approved`), submit_mission_votes { votes, voter_ids? } (returns winner, shuffled votes,
nazi_vote_count, scores, game_winner, next_round), forfeit { faction }, check_win_condition,
end_game (returns the next game's chef index).

## Rule/Flow Notes

- 5-player rooms still behave exactly like before.
- Rooms can now grow to match the supported engine presets up to 11 players.
- If the client does not provide a ruleset, the server infers the matching preset from the room size at start time.
- Mission team sizes are read from the selected ruleset, so preset-specific mission layouts are enforced by the server and Python engine together.
- Confidence vote is public and requires strict majority yes to proceed.
- If confidence fails (NO majority or tie), the same chef proposes again for the same mission.
- Mission outcome:
  - at least one nazi vote => nazis win mission,
  - all communist votes => communists win mission.
- Game ends when a faction reaches 3 mission wins.
- Chef rotation advances once per round (mission), never on a rejected proposal, and persists across games.

### Supported presets

- PRESET_5J
- PRESET_6J
- PRESET_7J
- PRESET_8J
- PRESET_9J
- PRESET_10J
- PRESET_11J

Notes:

- 6-player mission sizes match the 5-player layout.
- 7, 9, and 11-player mission sizes currently use placeholders in the engine and will raise an explicit error if a round tries to use them.
- 8-player mission sizes reuse the 7-player placeholder layout for now.
- 10-player mission sizes reuse the 9-player placeholder layout for now.

## Notes for Integrators

- Room and session state are in-memory only.
- No auth/account system is included.
- Reconnection support relies on the client rejoining the same room with the same playerId.
